# The four tables

This is the shape the auth-and-roles convention needs. It is written as
tables rather than as code, because every stack spells a model differently
and the columns are what matter. `rbac.py` beside this file reads only four
of these columns: the project's primary key, and the membership's project,
user and role.

Types are given in plain words. Use whatever your database calls them.

## Organisation

Who a user and a project belong to. An id, a name and a timestamp, and
nothing else. An engagement that needs more adds it here.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key. Generated by the application, not the database. |
| `name` | text, up to 200 | Unique. |
| `created_at` | timestamp | Written by the database, not by the application. |

Two rows written in one request must agree on the time, which is why the
database writes it.

## User

One person with an account. Email is the username, so there is no separate
login name.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key. |
| `email` | text, up to 320 | Unique. Trimmed and lower-cased before every read and write. |
| `name` | text, up to 200 | Shown on screen, and the initials come from it. |
| `password` | text | A hash. Never the password itself. |
| `org` | reference to `Organisation` | Deleting an organisation with users on it is refused. |
| `created_at` | timestamp | Written by the database. |
| `disabled_at` | timestamp, nullable | Null means active. |
| `is_superuser` | boolean | One flag. A super admin sees every project. |

Three notes on the columns above.

The column is `is_superuser`, which is Django's own name, and the application
reads it through a property called `is_super_admin`. Two booleans would drift
apart, and Django's permission checks already short-circuit on its one. Any
stack should keep one column here, whatever it calls the reader.

`disabled_at` is a timestamp rather than a boolean, because when somebody was
disabled is worth keeping. A disabled person can neither sign in nor keep the
session they already had.

Lower-casing the whole email, not just the domain, is what stops `Ada@x.test`
and `ada@x.test` becoming two accounts. Change that normalisation later and
you lock people out of accounts they already have.

## Project

One piece of work, with people on it. Three columns in the template. An
engagement adds what it needs, in the same commit as the migration.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key. |
| `name` | text, up to 200 | Not unique. |
| `created_at` | timestamp | Written by the database. Also the default sort. |

## ProjectMember

One row per person, per project, per role. This table is the whole of the
access rule. A row means you may see the project. No row means you get a 404.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID | Primary key. |
| `project` | reference to `Project` | Deleting a project deletes its memberships. |
| `user` | reference to `User` | Deleting a user who is on a project is refused. |
| `role` | text, up to 64 | A plain string. `owner` is the only value shipped. |
| `added_at` | timestamp | Written by the database. |

There is a unique constraint on `project`, `user` and `role` together. That
is what makes adding the same member twice a no-op rather than a second row.

`role` is a plain string and not a fixed set of choices, so a new role is a
row rather than a migration. It is a per-project value, which is why it is a
column here and not a global group on the user.
