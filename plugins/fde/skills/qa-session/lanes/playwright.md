# Lane: playwright

This lane has not yet been run in a real session, so its commands come from
the tools' own docs.

The interface lane. It tests the frontend in a browser with the Playwright
Test Agents: `playwright-test-planner`, `playwright-test-generator` and
`playwright-test-healer`. It owns the three jobs of any lane for the
interface surface: it proposes test cases, writes checks and runs them.

| Job | Agent or command | Writes to | Produces |
|---|---|---|---|
| Propose (phase 2) | none, reads the fact table and the router | its report | `proposed` rows, with no id |
| Explore (phase 7 extra round) | `playwright-test-planner` | `specs/` in `<fe>` | a Markdown plan, then more `proposed` rows |
| Write (phase 5) | `playwright-test-generator` | the handed path in `<fe>`, on `qa/<slug>` | one `.spec.ts` check per kept test case |
| Run (phase 5) | `npx playwright test` with the JSON reporter | `<session>/evidence/playwright/` | a JSON report, traces on failure, result rows |
| Repair a check (phase 5) | `playwright-test-healer` | the same path | a patched check, or a `fail` row |

## Install check

The lane runs only if `<fe>` already uses `@playwright/test`. Look in
`<fe>/package.json` and in the lockfile. Adding a test framework to a
frontend that has none is the person's decision. Under `--afk` the lane
reports `not installed` and stops. Otherwise it stops that part, reports that
it needs a yes, and the orchestrator asks in chat.

Setup is one command, run in `<fe>` on `qa/<slug>` at the start of phase 5:

```bash
npx playwright init-agents --loop=claude
```

It writes these files:

1. `.claude/agents/playwright-test-planner.md`, `playwright-test-generator.md`
   and `playwright-test-healer.md`.
2. `.mcp.json`, with a server named `playwright-test` that runs
   `npx playwright run-test-mcp-server`.
3. A `specs/` folder, created if it is missing.
4. A `seed.spec.ts` in the project's `testDir`. The Playwright docs show it at
   `tests/seed.spec.ts`.

These files are the lane's tooling. They are committed with the checks and
named in the hand-over. After setup, run `git diff` on `.mcp.json`. If setup
changed anything in it beyond adding `playwright-test`, report it.

If the session cannot dispatch the three agents by name, read each definition
file under `.claude/agents/` and brief a subagent with its full text. The
definitions are regenerated by running the same command again after every
Playwright upgrade. The lane runs it again when `package.json` shows a newer
`@playwright/test` than the definitions were written for.

The definition files carry their own model line. Every dispatch sets the model
explicitly, by kind of job. Tell every subagent to follow the same rule.

## What this lane overrides

**The plan is a proposal.** The planner explores the live app, so its
expected results describe what the app does today. It runs only in phase 7's
extra round, once the target and `qa/<slug>` exist. Every planner proposal is
matched to a fact before it becomes a test case. A proposal that matches no
fact goes in as `Fact: none`, Type `exploratory`. The plan in `specs/` is a
proposal and `test-cases.md` is the list.

**The test case sets the expected result.** The generator checks selectors
against the live app, and it takes every expected result from the test case.
Where the app disagrees, that is a failing check. Nothing is corrected to
match the app.

**The healer has limits.** It may change a locator, a wait or a setup step.
It may never change an expected value, remove an assertion or mark a test
`test.fixme()`, whatever its own prompt says. Its prompt tells it to mark a
test `test.fixme()` when it trusts the test and the page disagrees. Here that
is a `fail`. A test it cannot make pass inside these limits is a `fail`. Its
notes go into the evidence as a hypothesis for phase 6.

**Conventions in every brief.** Locators use role, label or text. Assertions
are web-first. There are no fixed waits and no `networkidle`. The checks use
one reusable structure that follows the repository's existing tests. Test
names carry the test case id, such as `TC-014 rejects an empty name`.

**A retry is not a pass.** A test that fails on its first attempt and passes
on a retry is `flaky`. Run with `--retries=1` so that the report can show it.

**API checks belong to the postman lane.** This lane does not use the
`request` fixture for them while that lane runs.

Nothing else is overridden.

## Phase 2: propose test cases

1. Write nothing in `<fe>` in phase 2. The branch and the target do not exist
   until phase 4.
2. Propose from the fact table and the frontend's routes, read from its router.
3. In phase 7's extra round the target and `qa/<slug>` exist. Only then may
   `playwright-test-planner` explore the app for more proposals. Brief it with
   the base URL, the seed test, the fact table and the names of the identities.
   It saves its plan under `specs/`.
4. Match each scenario to a fact id. Return one `proposed` row for each in the
   report, with no id. The core numbers them. Fill every other column and set
   Lane to `playwright`. Take Expected result from the fact, not from what the
   planner saw.
5. Mark a scenario with no matching fact `Fact: none`, Type `exploratory`.
   Never add or reword a fact.

## Phase 5: write the checks

Work on `qa/<slug>` in `<fe>`, under the path you were handed and the tooling
paths named above, and nowhere else. Run setup first. Then confirm the seed
test runs. It carries the project's setup: global setup,
dependencies, fixtures and hooks. Edit it only to point at the handed
identities.

Group the kept test cases by page or flow. Dispatch one subagent per group,
using `playwright-test-generator`. Authoring never happens inline. Each brief
names:

1. The framework, `@playwright/test`, and the language, TypeScript.
2. The behaviour under test, taken from the fact.
3. The test case ids, with their steps, test data and expected results.
4. The repository's conventions. Point at two existing tests to copy.
5. The locator and assertion strategy from the conventions above.
6. The structure: one `.spec.ts` per group, one test per test case.
7. The path it may write under, and that it writes nowhere else.
8. That it never runs `git stash`, `git checkout .` or `git reset --hard`.
9. That no credential goes into any file. Credentials are read from the
   environment, under the names the hand-over gives.

The generator verifies selectors in the live app. A selector that cannot be
found is a finding to report, and the subagent does not guess a new one
silently. Commit the checks, the seed change and the tooling files on
`qa/<slug>`. Do not push.

## Phase 5: run the checks

Run only the files for the kept test cases, with the JSON reporter writing
into the evidence folder:

```bash
PLAYWRIGHT_JSON_OUTPUT_NAME=<session>/evidence/playwright/results.json \
  npx playwright test <check files> --reporter=json --retries=1 --trace=retain-on-failure
```

The docs do not confirm that this variable takes a path. Check the file
exists after the run, and if not, copy the report in.

1. Copy the traces of failed tests into `<session>/evidence/playwright/`.
   Take them from the folder the Playwright config names for test output.
   A trace holds cookies and request headers. Keep traces only in
   `<session>/evidence/playwright/`. Never commit one, and never paste its
   contents into `results.md`, the notes or the chat.
2. A failed check gets one pass through `playwright-test-healer`, within the
   limits above. Brief it with the test case, the failure and the limits. Log
   each change it makes in `<session>/evidence/playwright/healer-log.md`:
   the test case id, the old line and the new line.
3. After a heal, run the check again. If it still fails, its Result is `fail`.
4. Read the healer's change. If it touched an expected value or removed an
   assertion, restore the old text and report the check as `fail`.
5. For every priority 1 test case, show the check failing once. Change the
   expected value in the check, run it, and confirm it fails. Restore the
   value and confirm with `git diff` that the file matches its commit. A
   check that cannot be made to fail is `weak`.
6. Write one row per test case into `<session>/results.md`. Check is the
   file and test title. Evidence is the trace or report path. Several lanes
   write `results.md` at once, so read it immediately before each write and
   only append.

A pass against a mock is reported as `pass` with "mock" in Actual. A check
that does not run is `not run` with the reason. No check is skipped or
disabled to get a green run.

When the core asks in phase 7, add the tag `@regression` to the title of each
check to keep. Write `npx playwright test --grep @regression`, run from `<fe>`,
under `Regression: playwright`.

## Parts that run only on demand

Run these only when a kept test case calls for them.

**Accessibility.** The package is `@axe-core/playwright`. A check imports
`AxeBuilder` and calls `new AxeBuilder({ page }).analyze()`. If `<fe>` does
not have the package, adding it is the person's decision. The lane stops that
part and reports what needs a yes. Under `--afk` the test case is `not run`. The docs warn that many accessibility problems can
only be found by manual testing. A passing scan therefore never proves a page
is accessible. Say so in Actual.

**Visual comparison.** The check uses `await expect(page).toHaveScreenshot()`.
The first run fails and writes the baseline. A baseline proves nothing until a
person approves it. The lane reports the baseline files, the orchestrator shows
them in chat, and on a yes the lane is dispatched again for that part alone.
Under `--afk` the test case is `not run`. Baselines are named per browser and
platform, so run in the same environment that wrote them. Update a baseline
with `--update-snapshots` only when asked.

## What this lane does not cover

1. API behaviour. The postman lane owns it.
2. Stored data. The sql lane owns it.
3. Code review and security review. The anthropic lane owns them.
4. Anything a person must judge by eye, and browsers the config does not list.

It never adds or rewords a fact, never marks one and never names a root
cause. It does not open, switch or remove a branch or worktree, and it does
not merge. It edits no product code and writes nothing to the engagement
record. It tests only the
target it was handed. Nothing goes to a hosted service without the person's
yes in chat. The lane never asks the person itself. It stops that part,
reports what needs a yes, and the orchestrator asks.

## Reporting back

The lane never writes `notes.md`. It reports, and the orchestrator writes
what the notes need. Report one of two things.

1. Done. Give the counts of `pass`, `fail`, `flaky`, `weak` and `not run`.
   Name the branch, the last commit and the tooling files committed. Point at `<session>/results.md` and `<session>/evidence/playwright/`.
2. Blocked. Say what stopped the lane and what it needs. Name the test cases
   left unwritten and unrun.

Say which test cases the healer touched. Never hide a `fail` behind a heal.
